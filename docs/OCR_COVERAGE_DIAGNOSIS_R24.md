# OCR 仅整理出 4—5 项：原因与修复建议

本轮仅定向排查、生成建议和虚构输入证据。没有修改产品源码、清单、医学规则、数据库或历史交付物，没有启停服务、读取用户浏览器记录或再次调用腾讯 OCR。

## 结论

主要问题是**报告采集范围被现有指标字典限制**：文字识别完成后，程序直接把内容筛成少数已知医学指标，没有独立的“整张报告项目”层。当前支持18种指标，还包含体温、心率等；这不是完整血常规字典。红细胞、红细胞压积、平均红细胞体积、淋巴细胞百分比等即使文字完整，也不会生成可核对项目。

其次存在可复现的解析覆盖缺口：部分版式遇未知行后停止后续整理；结果后的升降箭头、单位拼写差异、表头变化会进一步减少候选。它们是保守保护条件的副作用，修复必须同时维持防错列、防取参考值等保护。

这不是“最多只能识别5项”的数量限制，也未发现按低置信度丢弃候选的逻辑。本轮没有证据证明腾讯把整张图只识别成5个项目，亦不能证明供应商完全没有漏字。

## 本轮实际复现

| 虚构输入对照 | 实际结果 | 含义 |
| --- | --- | --- |
| 同时给6种已支持指标 | 6项 | 没有4/5项硬上限 |
| 红细胞等4种未支持项目，完整名称/值/单位 | 0项 | 字典白名单是主要范围限制 |
| 无坐标、明确表头、白细胞及CRP | 2项 | 正控制 |
| 同表最前插入红细胞未知行 | 0项 | 后续已知项目也未整理 |
| 同表在白细胞与CRP之间插入未知行 | 1项 | 无坐标路径在首个无效行退出 |
| 标准单位与小写 `10^9/l` 对照 | 1项→0项 | 单位匹配覆盖有限 |
| 同行数值附 `↑` | 0项 | 未将异常标记与数值分离 |
| 双栏合成表，基线5项，单项数值附 `↑` | 5项→4项 | 可单独造成已知项目减少 |
| 双栏表仅把“中文名称”改成“检验名称” | 5项→0项 | 特定表头白名单覆盖有限 |
| 已知指标，仅把置信度降至0.01 | 仍1项 | 当前候选未按置信度截断；不证明低置信度可靠 |

缺单位仍拒绝，这是应保留的保护。未知行触发停止也有防错位目的，不能机械删掉 `break` 或任意滑动寻找下一个数值。以上反例可解释其他报告的减少，但不证明它们都发生在用户当前这张图。

## 推荐修复结构

```text
OCR原始证据（原样保留）
  → 报告行整理：名称／原值／单位／参考范围／升降标记／来源
  → 用户逐项核对：可修改，无法配对的内容明确提示
  → 同一个本机Store事务保存
  → 显式标准化映射：已确认、名称及单位可信的项目
  → 既有三套医学规则
```

1. 报告层先保留项目，再判断是否认识。未映射项目也可核对并保存，保留原始字面值和来源；歧义行单列为“需要核对”，不伪造配对成功。医学规则继续只消费明确支持且用户确认过的指标。
2. 在同一轮修正同类解析覆盖：将升降标记独立解析；显式登记单位及表头变体；未知名称不再阻断几何可靠的后续行。无坐标且无法证明行边界时保留原文，不猜测对齐。维持双栏区域边界、冲突拒绝、参考值不充当结果、百分比不充当绝对计数等反例。
3. 页面分别展示“已整理项目、需要核对内容、识别原文”。不把文字片段数充当项目总数，不把医学可用项数充当整报告覆盖率。沿用现有“选资料→核信息→存数据”。
4. 先保留现有腾讯服务，以固定虚构报告集测量文字漏读率与行配对准确率；若确有供应商能力瓶颈，再评估表格OCR。此时不能靠换供应商解决本机字典和保存模型的限制。不建议引入大模型补猜结果。

## 可以独立验收的最小实施切片

**范围：常见血常规报告的整表采集闭环，不承诺所有检验报告通用。** 开工先冻结支持版式和项目验收清单；报告层对未映射项目保留原文及核对状态。完成“整表候选→用户逐项确认→本机保存→详情与来源→加密备份与恢复”。当前18种指标和三套规则行为保持兼容。

需先批准数据契约：原报告项目与标准化指标的关系、记录版本、旧数据兼容、来源及修改快照、备份格式和恢复验证。采用现有权威Store，不增第二存储引擎；不能把未知项目硬塞进旧枚举或仅藏在备注中宣称结构化完成。

拟写集涉及003工程内：独立报告行解析模块；候选与版本化模型/来源校验；录入核对和详情投影；同一Store事务封装及备份恢复验证；白名单测试、构建生成清单与本批文档证据。详细文件级上限应在实施方案中冻结。本轮建议不授予主PTDS、网关计费、密钥、真实数据或公网操作权限。

验收须包含：冻结报告清单逐行有去向；未知行不吞后续可靠行；双栏、箭头、单位/表头变体和歧义反例；用户核对后事务保存及新进程读回；备份恢复逐项一致；旧记录兼容；10倍规模下的明确耗时/内存门槛。新模块无全局锁、网络工作不入Store事务，延续现有有界资源；正式数字与写集在实施前确定。
