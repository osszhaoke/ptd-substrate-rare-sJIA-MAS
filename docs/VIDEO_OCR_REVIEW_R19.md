# Alpha 0.1 视频反馈：识别后仍要手填

结论：用户反馈成立。视频显示已经选择照片、勾选上传同意、启动识别；随后页面提示“图片识别好了”，核对页却没有任何自动填写的指标，最终用户自行添加指标才能保存。保存详情保留185行识别原文，说明文字识别返回了材料，**“文字变成可核对指标”的闭环没有完成，页面又没有解释这个区别。**

本轮仅分析指定视频、当前源码和合成对照；未修改产品源码、启停线上服务、请求真实OCR、读取用户浏览器/健康库/费用账本。新增结论仅登记到文档与当前债务状态，不实施修复。视频中的医学数值不作临床解释。

## 画面证据

视频长度约63秒。采用全段约每3秒画面采样及关键时刻原分辨率帧精读；音轨未转写。下述时间使用视频时间，不以手机状态栏时间代替。

| 时段 | 可观察到的动作/结果 | 能证明什么 |
|---|---|---|
| 约0–6秒 | 在录入页选择照片；页面显示已选文件名，在线识别区域展开 | 选择照片动作完成，尚不能单凭选择动作认定已上传 |
| 约8–10秒 | 上传同意已勾选，“上传并识别”进入禁用等待状态，出现“取消等待” | 实际启动了识别路径，不能把问题解释成用户只选图未点识别 |
| 约21.8秒 | 识别仍等待时，底部“直接手填”主按钮仍可见，画面有触碰标记 | 主操作与等待状态冲突，容易让人提前进入手填；不能仅凭触碰证明它导致零候选 |
| 23.5秒 | 出现“图片识别好了，请对照原图核对”；“核信息”页只有日期、添加指标及备注，没有预填指标行 | 明确的反馈与实际结果落差：看起来识别完成，用户却无内容可核对 |
| 27.0秒 | 尝试进入保存时提示“请先填一些检查结果、身体情况或病程” | 空核对页被后续有效性检查阻挡，用户需要补填才能继续 |
| 约30–43秒 | 用户手动添加一项、填数值，再本人勾选确认保存 | 完成的是手填回退路径，不是自动填入后核对的验收 |
| 46.0秒 | 详情显示“识别原文，共185行”，已保存指标标注“手工填写” | 原文有返回并保留；这不证明自动候选成功，也不证明原文字字正确 |

因此可以对用户直接说明：“照片里的文字读出来了，但系统没能把这份报告整理成可核对的指标。页面却提示完成，让你落进空表单，所以才只能手填。这是产品需要补齐的环节。”

## 源码核对与证据边界

实际路径为：腾讯高精度识别返回文字/坐标 → gateway/tencent.py 映射并保留ledger → web/adapters/ocr.js校验 → candidates提取指标 → 核对页 → 本人确认事务保存。供应商读出文字与PTDS填好指标是两步，不是同一个成功条件。

1. **已确认：零项仍走统一成功分支。** web/app/main.js:84–86把candidates结果直接渲染，然后无条件进入第2步并提示“图片识别好了”。没有根据0项、部分可用或有候选分别显示结果。candidates为空数组时，正好得到视频中的空核对页。原文保留和本人确认保护没有被绕过，未观察到自动保存或资料丢失。
2. **已确认：五列双语表格存在适配缺口。** 视频详情露出的表头为“英文／中文名称／结果／单位／参考范围”。web/domain/state/ocr_fragments.js:16、33仅接受3或4个单元片段；无坐标分支还要求“项目/检查项目/检验项目”表头，不识别“中文名称”。当前候选器另只接受明确支持的项目别名和单位，不能把所有文字直接当指标。
3. **尚未唯一确认：这次真实响应究竟在哪条规则被拒绝。** 没有读取该用户的完整185行响应及坐标；真实供应商可能把一行合并成一个片段，也可能拆成多列。现有画面与源码足以定位到候选整理/呈现环节，并确认五列形状的支持不足；不足以断言本次必然仅由列数造成，或归因于某一单位拼写。
4. **已确认的引导问题。** 在线识别入口默认折叠，主按钮“直接手填”在选图后仍沿用；等待期间没有明确的“正在识别”主状态。前者可由模板与选图回调核对，后者在视频中可见。它们加重困惑，但不替代上面的功能断点。

## 只读合成对照

在独立分析目录运行当前真实candidates函数，未改函数、断言、产品文件或服务，也没有调用云端。只采用自行构造的虚构数值与表格，不把视频中的真实材料制成工程测试夹具。

| 输入 | 无坐标结果 | 有完整坐标结果 |
|---|---:|---:|
| 项目／结果／单位／参考范围，四列控制 | 1项 | 1项 |
| 英文／中文名称／结果／单位／参考范围，五列双语形状 | 0项 | 0项 |

同一合成指标如果把项目、数值和单位并成单个明确文本行，原解析器可提取1项。这个对照表明片段组织方式会影响结果，不能把五列合成反例冒充这次真实响应的精确重放。

当前已知问题登记：新增1项P2录入闭环/结果反馈问题（零候选仍表现为完成，并将用户带入空核对页）；五列支持不足和等待/手填引导作为关联修复范围。不是发现P0/P1、医学计算错误或数据丢失。原57项作者检查与独立续审的实际结果仍是其既有窗口事实，但没有覆盖这个输入形状/零候选用户结果，不足以据此说所有报告已支持。

## 建议的最小修复片（本轮未实施）

目标是“对明确可解析的双语五列表格填入候选，对无法整理的内容如实说明”，不是让用户上传后仍从空表单猜下一步。

- **选图：** 显示“照片已选，尚未识别”；识别入口作为明确主动作，手填作为次要选择。仍需用户同意后才上传，不静默上传。
- **等待：** 明确显示“正在识别”；切换手填需明确取消本机等待，沿用已有取消与过期结果保护，不自动重发付费请求。
- **结果：** 有候选时显示“已整理N项，请核对”；零项时显示“读到了文字，但还没整理出可填写的指标”，保留原文/图片对照及手动补填入口，避免统一完成提示和无解释的空表单。有候选不等于整份报告识别完整，不能编造总项数或完整率。
- **解析：** 支持明确表头下的英文/中文双语列，核对项目映射、结果列、单位与来源；参考范围不得误作结果。歧义、缺失单位、名称冲突继续留给用户核对，不能为了填上而猜数值。
- **保存：** 仍是核信息后本人确认；不修改医疗规则、DB、备份、费用、OCR服务商或权限。

拟涉及现有OCR片段/候选模块与录入流程/展示模块；main只保留接线，反馈放录入模块，控制现有主文件增长。读取/解析在前端已有路径，无新增全局锁、后台轮询、存储引擎或依赖；保留现有2万片段/100候选上限，继续测原十倍规模。该片验收需要真实UI覆盖：四列对照、双语五列、零项、部分可用、单位/参考范围歧义、等待转手填，以及本人确认前正式记录为0。

先用虚构同版式夹具证明本次零项反馈可复现并由修复前行为断言捕获，再修复和完整重验；上线和实机结果另据实际登记。本报告不是已修复、已部署或新增独立验收声明。
